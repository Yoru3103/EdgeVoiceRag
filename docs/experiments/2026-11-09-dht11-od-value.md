# DHT11 IRQ前置版本的GPIO方向错误与接口修订

日期：2026-11-09。使用者在板端加载0.2.0-irq-first后，连续读取出现：

```text
gpiod_direction_output: tried to set a GPIO tied to an IRQ as output
failed to drive data GPIO low: -5
```

这是上一版采集修订引入的接口错误，发生在发送起始信号前；不能归为原先的71～82沿超时，也不是传感器坏帧。

## 原因与修订

核对本机6.1.141 SDK内核drivers/gpio/gpiolib.c：gpiod_direction_output首先检查FLAG_USED_AS_IRQ和FLAG_IRQ_IS_ENABLED，命中即返回-EIO，然后才处理开漏标志。上一版将“开漏GPIO允许IRQ共用”误解为允许在IRQ已启用时再次调用direction_output；该判断不成立。

版本 **0.2.1-od-value** 保留IRQ前置和82沿严格解码，将DATA的运行时操作改为已配置开漏描述符的gpiod_set_value：

- 0：通过gpiolib开漏路径拉低，并读取线路确认低电平；失败则释放IRQ，不发布缓存。
- 1：通过开漏路径释放，电平由外部3.3V上拉提供。
- 不再在IRQ已启用后调用gpiod_direction_output，也不使用raw接口或修改内核内部标志绕过保护。
- 去掉probe和清理中的重复direction_input操作，统一保持配置好的开漏语义。

依据：[Linux GPIO消费者API](https://docs.kernel.org/driver-api/gpio/consumer.html)、[Linux6.1 gpiolib实现](https://github.com/torvalds/linux/blob/v6.1/drivers/gpio/gpiolib.c)。gpiod_set_value返回void，底层控制器错误由GPIO框架记录；显式低电平回读和后续帧校验不能代替真实波形验证。

## 离线回归与构建

新增tests/test_acquisition.py：从实际驱动源码取出采集、IRQ handler和边沿打印函数，配合GPIO/IRQ资源模拟及输入波形编译执行；不维护第二份采集函数。模拟明确拒绝在启用IRQ时使用direction_output，重现上一版-EIO。

新版覆盖6类：正常帧、连续两次重新测量、IRQ申请失败、线路拉低失败、截断帧、等待被中断。检查返回结果、失败不发布温湿度/缓存、IRQ释放和线路释放。普通与ASan/UBSan各执行一遍，通过。模拟不执行probe、真实控制器或中断调度，不能验证硬件时序与成功率。

另外共享帧解析器的10组语义用例，本轮普通与ASan/UBSan均通过；新ARM模块编译通过：

- 版本：0.2.1-od-value。
- vermagic：6.1.141 SMP mod_unload aarch64。
- 产物：.cache/dht11-odfix-20261109-f4zj_tyg/edge_dht11.ko（Git忽略）。
- SHA256：73ab295b6bcca30a470a0d235c70a311a5abb7d2eeb6baf778971e702d193f7a。

本次没有操作板端。使用者应手动加载后先核对/sys/module/edge_dht11/version，只读一次温度确认-EIO方向错误不再发生，再继续独立10次温度采样。整体漏沿稳定性仍未验证通过。

后续用户实测：0.2.1温度独立10次为4成功、6失败，方向保护错误未重现，但漏沿/解码稳定性未通过；见[后续记录](2026-11-09-dht11-4-of-10.md)。
