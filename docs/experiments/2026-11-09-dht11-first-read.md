# DHT11 首次成功读取记录

日期：2026-11-09。证据来自使用者提供的RK3588终端日志；本次由智能体离线分析，没有操作开发板。

## 观察结果

- 设备为 `edge_dht11`，位于 `iio:device1`；GPIO IRQ为154。
- 日志显示驱动在启动后约361.895秒重新注册，本次读取发生在约405.475秒。
- 温度sysfs读取返回31000，即31℃。
- 驱动记录 `captured 83 edges`，最终解码温度31000、湿度38000，即31℃ / 38%RH。
- 前期超时日志仍保留在dmesg中，不能将它们当成本次成功读取又发生的错误。
- 启动参数中未出现threadirqs；这不足以排除其他中断延迟原因。

## 帧的离线核验

将使用者日志中的脉宽按当前驱动阈值50µs分类，成功的offset=1对齐得到五字节：

```text
湿度整数  湿度小数  温度整数  温度小数  校验
38        0         31        0         69
(38 + 0 + 31 + 0) & 0xff = 69
```

数据位高电平约23.9～26.5µs表示0，约70.3～72.9µs表示1，能被当前阈值区分。这里是IRQ记录的时间差，不等于逻辑分析仪测到的电气波形。

`lost synchronization at edge 3` 来自首先尝试offset=2失败；代码继续尝试offset=1后成功，不是本次读取的最终错误。当前解码器原本就允许多种起始偏移，不能据此认定所有帧均存在一个固定偏移。

## 当前结论与下一步

已验证一帧传感器数据采集和解码成功，并通过校验和；湿度38000来自同一帧的解码日志，用户本次只直接读取了温度sysfs节点。尚未完成连续成功率、长时间稳定性和C++ Agent真实温湿度联调验证。

此前诊断补丁增加采集结束后的明细和超时注册耗时，没有改变IRQ申请顺序、解码阈值或83边沿门槛。单次成功不能证明早期50～68边沿超时的根因已解决；成功路径不会打印release-to-IRQ-ready，该字段目前只在超时报错中出现。

下一步由使用者关闭动态调试后进行10组、间隔3秒的温湿度读取，观察每组是否均返回有效值。温度与湿度连续读取通常复用2秒缓存中的同一帧，所以10组不是20次独立测量。测试步骤见[DHT11说明](../hardware-dht11.md)。
